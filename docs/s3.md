# S3

An S3-compatible view of a user's library, so they can point `rclone`, the AWS
CLI, Cyberduck/Mountain Duck or `s3fs` at it. Paid-only, read-only except for
`torrents`. It is the same virtual filesystem WebDAV serves — see
[webdav.md](webdav.md) — with a different wire format on top.

```
services/vfs      FileInfo / FileSystem / HTTPError — the protocol-neutral contract
services/libfs    the library tree (roots, torrents, content) implementing it
services/webdav   RFC 4918 on top of it        handlers/webdav  routing
services/s3       S3 REST on top of it         handlers/s3      routing
```

Nothing in `services/libfs` knows which protocol is asking. Adding an operation
to the tree lands in both at once; a change in folder layout changes both, by
construction. That is the point — the user-visible structure is identical
whichever protocol they mount.

## Buckets are the top-level folders

| Bucket | Contents | Writable |
|--------|----------|----------|
| `torrents` | `<name>.torrent` per library item | yes (PUT / DELETE / copy-rename) |
| `all` | every torrent as a folder | no |
| `movies` | recognized movies | no |
| `series` | shows and episodes | no |

`bucket + "/" + key` is concatenated straight into a filesystem path
(`listing.go:vfsPath`), which is the whole reason the folders are exposed as
buckets rather than as prefixes inside a single one.

**Path-style addressing only.** Virtual-host style (`bucket.endpoint`) would
need wildcard DNS. Clients must use `force_path_style` / `--endpoint-url`, which
is the default for a non-AWS endpoint anyway.

## Credentials: derived, not stored

The endpoint is `https://webtor.io/s3` (`handlers/s3.MountPath`) — no URL alias,
no token in the path, because S3 authenticates in headers.

- **access key id** = the user's `access_token` row with `name = "s3"`, scope
  `s3:read` / `s3:write`. Issuing and rotating reuse `at.Generate` /
  `at.Regenerate` untouched.
- **secret access key** = `base64url(HMAC-SHA256(<signing secret>, "s3:" + access key))`
  — `services/s3.DeriveSecretKey`. Nothing extra is stored, so there is no
  migration and no new user-keyed table (and therefore nothing to add to the
  GDPR export beyond the access token that was already there).
- **signing secret** = `S3_SIGNING_SECRET`, falling back to `SESSION_SECRET`.

> Rotating the signing secret invalidates **every** user's S3 configuration at
> once, exactly as rotating `SESSION_SECRET` drops every session. That is the
> price of not storing secrets; if it ever becomes a problem, move the secret
> into its own column and keep `DeriveSecretKey` as the fallback for rows that
> predate it.

Requests are verified with real SigV4 (`services/s3/auth.go`), header and
presigned-query flavours both. A wrong secret is rejected — the access key is
not a bearer token.

## Request routing

Three things have to line up, and they are the non-obvious part:

1. **`services/s3.RegisterAccessKeyMiddleware`** runs *before*
   `services/access_token`'s own middleware (both are global `r.Use`, so order
   of registration in `serve.go` is the only lever). It puts the access key id
   from the signature into `?token=<key>`. Everything downstream —
   `auth.UserContext`, claims, `web.Context` — then works exactly as it does for
   WebDAV, with no S3-specific plumbing. It only forwards values that parse as a
   UUID, because the access-token middleware treats a malformed token as a 500
   and a typo in `rclone.conf` must not read as "webtor is broken".

   > **The token param is rewritten, never merged.** The signature is verified
   > against the key inside the signature, so a caller who could smuggle a
   > different `?token=` through the query string would be *authenticated* as its
   > owner while *signing* as themselves — i.e. read any account whose access key
   > id they know. The middleware therefore deletes any caller-supplied value
   > first, even when the request carries no signature at all, and
   > `handlers/s3.authorize` re-asserts that the two agree. Regression test:
   > `TestSuppliedTokenCannotOverrideSignature`.

2. **`handlers/s3.authorize`** replaces `at.HasScope` + `claims.IsPaid` on this
   group. Same checks, but it answers with an S3 error document: a client shown
   a bare 403 with an empty body reports something useless. Write methods
   additionally require `s3:write`.
3. **`handlers/s3.handle`** restores `c.Request.URL` from
   `c.Request.RequestURI` before handing off, because step 1 rewrote the query
   and the signature covers path *and* query. Same trick as
   `handlers/webdav.handleWebDAV`, for the same reason.

## Listing

`delimiter=/` — what every interactive client sends while browsing — maps onto a
single `ReadDir`. No delimiter means a recursive walk, which is what
`rclone sync`, `--fast-list` and `aws s3 ls --recursive` do, and it costs one
`ReadDir` (≈ one rest-api call) per directory. Those walks are cached per
`(user, bucket, dir)` in a `lazymap` for a minute and paginated from the cached
slice, so paging does not re-walk.

Walks are capped (`MaxWalkDirs` / `MaxWalkKeys`). **Hitting the cap is an error,
not a short answer** — a truncated listing that claims to be complete would make
`rclone sync` delete everything it did not see on the other side.

The cache holds every key of a walk, so its capacity is sized against memory
rather than hit rate (worst case ≈ `Capacity × MaxWalkKeys` entries resident).
web-ui has been OOM-killed by an unbounded cache before (the layout cache, now
bounded in `services/template`), so keep both numbers small and the TTL short.

Continuation tokens are just the last key emitted, base64url'd; objects and
common prefixes page as one sorted stream.

> Ops note: `libfs.DebugDirectory` logs one `msg="read dir"` line per directory
> it touches. That is how WebDAV problems get diagnosed in prod, but an S3
> recursive walk touches every directory in a bucket, so a single `rclone sync`
> writes a line per torrent. Worth knowing before reading Loki volume graphs.

## Two invariants that will silently break clients

### 1. The ETag must never look like an MD5

`rclone` treats a 32-hex-character ETag as the object's MD5 and verifies the
downloaded bytes against it. We never hash content, so every transfer would
fail. `etagFor` emits a 40-char sha1 of `key|size|modtime`, which fails
rclone's `^[0-9a-f]{32}$` check and is read as "no checksum available".
Covered by `TestETagIsNotAnMD5`.

### 2. `encoding-type=url` has to be honoured

Torrent names are full of spaces, brackets and non-ASCII. When a client asks for
URL encoding, keys, prefixes and delimiters go back percent-encoded (with
`url.QueryEscape`, matching the `QueryUnescape` clients decode with) and
`<EncodingType>url</EncodingType>` is echoed. Prefixes arriving from the client
are decoded before touching the filesystem. Covered by
`TestListObjectsURLEncoding`.

## GetObject is a redirect

Torrent content is served by the streaming chain, so `GET` answers `307` with
the export URL rather than proxying gigabytes through web-ui — the same choice
WebDAV makes. `.torrent` files under `torrents/` are small and local, so those
stream directly.

`HEAD` is answered from `Stat` alone and never opens the object: clients HEAD
constantly, and opening would mint a content URL each time.

`TestGetObjectFollowsRedirect` is the standing check that an S3 client actually
follows the redirect instead of surfacing the 307 as an error. If a client ever
turns up that does not, the only fallback is proxying the bytes, which changes
the bandwidth profile completely — treat that as a product decision, not a bug
fix.

## Writes, and the one place we bend S3 semantics

`torrents/` accepts PUT (add a .torrent to the library), DELETE (remove it) and
copy-with-`x-amz-copy-source` (rename it). Keys containing `.` or `..` segments
are refused outright: S3 would treat them as ordinary characters, but here a key
is concatenated into a filesystem path.

Two behaviours worth knowing:

- **CopyObject inside the bucket is a rename, not a copy.** The tree has `Move`
  and no `Copy`, and duplicating a library entry means nothing (same infohash),
  so a copy moves the source. A client doing a genuine same-bucket copy ends up
  with a rename. Clients that *move* (copy-then-delete) work correctly.
- **DeleteObject is idempotent**, per S3 — a missing key still answers 204. That
  is also what makes the copy-then-delete move flow above complete cleanly.

## What is not implemented

Multipart uploads, POST uploads, versioning, ACLs, tagging, lifecycle, bucket
creation/deletion. They answer `NotImplemented` or `AccessDenied` with a proper
S3 error document. `PUT` of a `.torrent` accepts the aws-chunked payload
encoding (`body.go`) but does not verify per-chunk signatures — the request
itself is signed and the payload has to parse as valid metainfo anyway.

## Testing

`services/s3/s3_test.go` runs the real `aws-sdk-go` client against the handler
over `httptest`, with an in-memory tree: listing (delimited, recursive, paged,
URL-encoded), HEAD, GET-with-redirect, presigned GET, bad-signature rejection and
the listing cap. For a client-level check, point rclone at a local instance:

```
[webtor-local]
type = s3
provider = Other
endpoint = http://localhost:8080/s3
access_key_id = <access token uuid>
secret_access_key = <derived secret from the profile page>
region = us-east-1
force_path_style = true
```

`rclone lsd webtor-local:` then lists the four buckets.
