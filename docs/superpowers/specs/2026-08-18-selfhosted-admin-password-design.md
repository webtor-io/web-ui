# Пароль администратора для self-hosted

Дата: 2026-08-18
Статус: утверждён (дизайн), ожидает план имплементации
Репозитории: `web-ui` (основная часть), `self-hosted` (проброс переменной, README, смоук-сценарий)

## Проблема

`services/auth/auth.go:459-462`: когда SuperTokens не настроен, на каждый запрос вешается
`registerAdminUser`, который создаёт (или находит) пользователя с email `admin` и кладёт в контекст
`IsAdminContext{} = true`. Никаких учётных данных не спрашивается.

Self-hosted не выставляет `SUPERTOKENS_SERVICE_HOST` — значит **любой, кто дотянулся до порта 8080,
является администратором инстанса**: видит и меняет библиотеку, настройки, подписки, файлы. README при
этом предлагает ставить `DOMAIN` в публичный адрес.

## Модель угроз (решение владельца)

Публичный интернет: инстанс может висеть на домене и быть найден сканерами. Отсюда argon2id,
ограничение перебора, Secure-cookie.

## Утверждённые решения

1. Пароль задаётся в профиле; при заданном пароле показывается окно входа.
2. `ADMIN_PASSWORD` в окружении — и предзаданный пароль для docker-compose, и путь восстановления.
3. CLI-команда сброса — второй путь восстановления, чтобы секрет не оседал в `docker inspect`.
4. Без пароля инстанс остаётся открытым, но с навязчивым баннером.

Расхождение, зафиксированное явно: при модели «публичный интернет» открытый по умолчанию инстанс —
это дыра, закрытая только вниманием пользователя к баннеру. Владелец выбрал этот вариант осознанно.
Смягчается тем, что `ADMIN_PASSWORD` закрывает инстанс с первой секунды.

## Три состояния

| Условие | Поведение |
|---|---|
| `ADMIN_PASSWORD` непуста | вход по паролю из переменной; смена через профиль запрещена |
| Переменной нет, хеш в БД есть | вход по паролю из БД; смена через профиль разрешена |
| Ни того, ни другого | автовход как `admin` (как сейчас) + баннер на каждой странице |

## Безопасность прода — неприкосновенное условие

Всё новое работает строго внутри ветки `if !s.hasSupetokens` (`services/auth/auth.go:460`).
Там, где SuperTokens настроен (прод), поведение не меняется. Это проверяется отдельным
негативным тестом: при сконфигурированном SuperTokens парольная ветка не активируется.

## Хранение

Колонка `password` в таблице `user` уже существует (`migrations/2_normalize_users.up.sql:5`), поле
`models.User.Password` объявлено (`models/user.go:17`), но **ничем не читается и не пишется** — наследие
до-SuperTokens эпохи. Переиспользуем её.

Отдельной миграцией переименовываем `password` → `password_hash`: в колонке лежит argon2id-хеш, и имя
не должно врать. Поле модели переименовывается соответственно.

Хеш пишется только пользователю с email `admin`. Алгоритм — argon2id (`golang.org/x/crypto/argon2`),
параметры по актуальным рекомендациям OWASP, соль на пароль, всё кодируется в стандартную строку
`$argon2id$v=19$m=...,t=...,p=...$salt$hash`, чтобы параметры можно было поднять позже без миграции данных.

## Поток авторизации

В ветке `!hasSupetokens` вместо безусловного `registerAdminUser`:

- пароль не настроен → `registerAdminUser` как сейчас (открытый доступ), в контекст кладётся признак
  «инстанс открыт» для баннера;
- пароль настроен → `registerAdminUser` вызывается только если в сессии есть отметка о входе;
  иначе пользователь анонимен и упирается в `HasAuth`.

`HasAuth` (`services/auth/auth.go:535-542`) сейчас отдаёт голый 401. Добавляется редирект на `/login`
для навигационных HTML-запросов; для XHR, JSON API и SSE сохраняется 401 (иначе фронт получит HTML
вместо ожидаемого JSON). Различение — по `Accept` и заголовку `X-Requested-With`/`Sec-Fetch-Mode`.

Роуты `/login`, `/logout` уже есть (`handlers/auth/handler.go:108-110`). В парольном режиме:

- `GET /login` рендерит форму пароля вместо SuperTokens-карточки (`loginCardFor`, там же:35);
- `POST /login` сверяет пароль, при успехе пишет отметку в сессию и редиректит на `from`;
- `GET /logout` снимает отметку.

Сессии уже настроены (`handlers/session/handler.go:60-83`): Redis-хранилище когда Redis доступен
(в self-hosted он есть), иначе cookie; `HttpOnly`, `Secure`, `SameSite`, срок 30 суток. CSRF-middleware
там же — форма входа обязана слать токен.

## Защита от перебора

На `POST /login`: ограничение попыток по IP через существующий `services/libapi.RateLimiter`
(`golang.org/x/time/rate`), задержка на неуспешной проверке, сравнение в постоянном времени
(даёт argon2id). Минимальная длина пароля — 8 символов, требований к составу нет: они гонят
людей в `Password1!`, а не в стойкие пароли.

## Интерфейс

**Профиль.** Секция «Пароль» по образцу существующих секций (`templates/views/profile/get.html`,
паттерн `{{ if not .Data.DisableWebDAV }}`): задать пароль, если не задан; сменить, если задан
(с вводом текущего); при `ADMIN_PASSWORD` — форма заблокирована с пояснением, что пароль
управляется переменной окружения.

**Баннер.** Пока пароль не задан — заметный блок на каждой странице с кнопкой «задать пароль».
Сворачивается на текущую сессию, но не закрывается навсегда: он единственное, что отделяет
открытый инстанс от чужих рук.

**Форма входа.** Одно поле пароля, без имени пользователя — администратор ровно один.

## Сброс

`web-ui admin set-password <новый>` — новая CLI-команда рядом с существующими семью
(`configure.go:15`). Пишет argon2id-хеш в БД. Плюс путь через `ADMIN_PASSWORD` и перезапуск контейнера.

## self-hosted

- `ADMIN_PASSWORD=${ADMIN_PASSWORD:-}` в `etc/webtor/common.template.env`;
- README: раздел про пароль администратора, оба пути восстановления;
- смоук-сценарий: без переменной `/` отдаёт 200; с `ADMIN_PASSWORD` `/` редиректит на `/login`,
  вход с верным паролем даёт доступ, с неверным — нет.

## Тесты

- приоритет `ADMIN_PASSWORD` над хешем в БД;
- отказ при неверном пароле и успех при верном;
- защищённый роут недоступен без отметки в сессии;
- **негативный контроль:** при сконфигурированном SuperTokens парольная ветка не активируется —
  иначе можно случайно сломать прод;
- срабатывание ограничителя перебора.

## Риски

1. **Ломает прод, если ветвление неверно.** Митигейт: негативный контроль в тестах, вся логика внутри
   одной ветки `!hasSupetokens`.
2. **Апгрейд существующих self-hosted установок.** Без `ADMIN_PASSWORD` поведение не меняется —
   инстанс остаётся открытым, добавляется только баннер. Ломающего изменения нет.
3. **Переименование колонки** затрагивает прод-БД. Митигейт: колонка не используется ни одним запросом,
   миграция чисто косметическая; при сомнении можно оставить имя `password` и ограничиться комментарием.
