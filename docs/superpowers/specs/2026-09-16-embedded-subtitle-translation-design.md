# Перевод встроенных субтитров потоком из транскодера — дизайн (2026-09-16)

## Решение владельца

Дорожку-источник берём **потоково из текущего транскодера**: content-transcoder уже отдаёт
встроенные субтитры в HLS сегментами WebVTT по мере транскода. Ничего не извлекаем целиком и
не скачиваем файл ради текста. (Вариант «извлечь всю дорожку через ffmpeg» отклонён: это
означало бы скачать всю раздачу.)

## Как транскодер отдаёт субтитры сегодня (проверено на стенде 2026-09-16)

Транскодер сессионный: `POST <file>~hls/session` → `{"id","duration"}`; дальше всё под
`<file>~hls/session/<id>/…` — тот же путь, что у плеера (`jobs/scripts/action.go`
`sessionBaseURL`/`sessionHLSURL`). `content-transcoder/services/hls.go` заводит для каждого
текстового потока субтитров `HLSStream{st: Subtitle, index: N}`; `StreamType` печатается как
`s`, поэтому плейлист — **`s<N>.m3u8`**, сегменты — **`s<N>-<k>.vtt`**. Мастер `index.m3u8`:
`#EXT-X-MEDIA:TYPE=SUBTITLES,GROUP-ID="subtitles",LANGUAGE="rus",NAME="Full (rus)",URI="s0.m3u8?…"`.
`N` — порядковый номер среди потоков субтитров, кроме `hdmv_pgs_subtitle` (`NewHLS`, `si++`).

Живой прогон (MKV с двумя текстовыми дорожками, через THP на premium-edge):

- `s0.m3u8`: 200, `application/vnd.apple.mpegurl`, `Cache-Control: no-cache`; тело —
  `#EXT-X-SESSION-OFFSET:0`, `#EXT-X-START:TIME-OFFSET=0`, `#EXT-X-MEDIA-SEQUENCE:0`,
  `#EXT-X-PLAYLIST-TYPE:EVENT`, без `#EXT-X-ENDLIST` пока ffmpeg работает (`PlaylistForStream`
  срезает его до завершения run'а). Сегменты растут по ходу транскода: через 20 с было 9,
  длительности неравные (63.7 с, 1.4 с, 2.4 с … — границы по cue, не по 4 с).
- Сегмент `s0-0.vtt`: 200, `text/vtt`, тело `WEBVTT\n\n00:45.107 --> 01:03.699\nМакс.` —
  **`X-TIMESTAMP-MAP` нет**, время cue — от начала текущего run'а. Абсолютное время фильма =
  cue + `#EXT-X-SESSION-OFFSET` плейлиста (после перемотки offset ≠ 0, квант 30 с).
- Неизвестный плейлист (`s0.m3u8`) → 404 `not found`; мёртвая сессия → 404
  `session not found`. Каждый запрос к плейлисту/сегменту делает `sess.Touch()` и при
  необходимости перезапускает ffmpeg — т.е. опрос сервисом продлевает и оживляет сессию
  так же, как плеер.
- Query (`api-key`, `token`) транскодер сам дописывает ко всем URI плейлиста
  (`enrichPlaylistData`) — сервису достаточно резолвить относительные URI против URL плейлиста.

THP: `extractMod` берёт мод из **последнего** `~`, всё левее уходит в `X-Source-Url`.
Значит `<file>~hls/session/<id>/s0.m3u8~tr:pt/x.vtt` → сервис `tr` с
`X-Source-Url = <thp>/<hash>/<file>~hls/session/<id>/s0.m3u8?<query>`; запрос к нему THP снова
разберёт как мод `hls` и отправит на транскодер той же ноды/пода (rendezvous по infohash).
Правок в THP и транскодере не нужно.

## Что меняется

### subtitle-translate: второй тип источника — HLS-плейлист субтитров

- `X-Source-Url` может указывать на `.m3u8` (определяем по расширению пути и/или
  `Content-Type: application/vnd.apple.mpegurl`). Тогда задача работает в **live-режиме**:
  1. читает медиаплейлист; для каждого нового `.vtt`-сегмента (URI относительно плейлиста)
     скачивает его, парсит WebVTT (без `X-TIMESTAMP-MAP`; время cue сдвигается на `#EXT-X-SESSION-OFFSET` плейлиста), добавляет cue в
     общий документ (дедупликация cue, пересекающих границы сегментов, по `start+end+text`);
  2. переводит батчами по мере накопления (тот же `Runner`, батч 50 cue, но батч закрывается
     также по таймеру ~10 с, чтобы не ждать 50 cue на медленной речи);
  3. перечитывает плейлист каждые 3–5 с, пока нет `#EXT-X-ENDLIST`; после него дожидается
     перевода хвоста и фиксирует финал в S3 как сейчас (ключ тот же: infohash+path+lang+model+
     promptVersion — `path` теперь путь плейлиста внутри `~hls`, поэтому ключ отличается от ключа
     приложенного файла того же фильма — это нормально).
- Прогресс: пока плейлист живой, `total` неизвестен → заголовок `X-Subtitle-Progress: <done>/<seen>`
  плюс новый `X-Subtitle-Live: 1`; клиент не считает `done == seen` финалом, пока есть `Live`.
  После `ENDLIST` и полного перевода — `N/N` без `Live`, `Cache-Control: public, max-age=86400`.
- Сессия транскодера: запросы сервиса к плейлисту/сегментам идут через THP на ту же сессию, что и
  плеер, и продлевают её так же, как запросы плеера; если зритель ушёл и сессия умерла (404 на
  плейлист) — задача завершается с `JobErrors{code="source_gone"}`, прогресс сохраняется в Redis
  на 24 ч, при следующем старте продолжится с сохранённых cue (плейлист с начала, cue уже
  переведённые пропускаются по ключу `start+end+text`).
- Лимиты как сейчас (`--max-cues`, `--max-source-bytes` на суммарный размер сегментов).
- Ключ артефакта: `X-Path` содержит `/session/<id>/`, поэтому сервис нормализует путь
  (`KeyPath`: `~hls/session/<32 hex>/` → `~hls/`) — все сессии одного файла и потока делят
  один ключ и один финал/прогресс.
- Идентичность cue между сессиями и прогонами — `start|end|нормализованный текст` в абсолютном
  времени фильма; прогресс в Redis хранит ключи cue по индексу, новая сессия переиспользует
  готовые переводы без повторного обращения к модели.
- В частичном (live) теле **нет непереведённых cue**: cue появляется в выдаче только с
  переводом (структурно пустые cue сохраняют слот). Исходный текст под AI-чипом читался бы как
  неверный перевод.
- **Задача останавливается сама, если ключ никто не опрашивал `--live-idle` (90 с)**: опрос
  плейлиста продлевает транскодер-сессию и перезапускает ffmpeg, то есть перевод без зрителя
  транскодировал бы файл целиком впустую. Прогресс сохраняется, `Live` остаётся.
- Батч закрывается по `--batch-size` (50) или по таймеру `--live-batch-wait` (10 с) с момента
  появления первого ожидающего cue; опрос плейлиста — `--live-poll-interval` (4 с).

### content-transcoder

Ничего менять не нужно, если THP пропускает `~hls/s<N>.m3u8~tr:<lang>/<name>.vtt`
(внешний мод `tr` с `X-Source-Url` = внутренняя цепочка `~hls/s<N>.m3u8`). Проверить на
стенде; если THP резолвит `~hls` только для `index.m3u8`/сегментов — точечная правка роутинга.

### web-ui

- `GetSubtitles`: элементу `MediaProbe` в HLS-режиме (когда стрим идёт через транскодер —
  `TranscoderSession != nil`) проставляется `Src = <hls base>/s<idx>.m3u8` — только как
  источник для перевода; воспроизведение встроенных дорожек остаётся через hls.js по `data-mp-id`.
  Индекс `idx` — порядковый номер текстового потока субтитров в пробе (как в транскодере:
  `HLSStream.index`), не абсолютный индекс потока — сверить с `NewHLS` в content-transcoder.
- `pickTranslationSource`: `MediaProbe` больше не пропускается, если у него есть `Src`
  (битмапные/forced по-прежнему исключены).
- Клиент: `parseProgress` учитывает `X-Subtitle-Live` (не финал), опрос продолжается; текст
  прогресса при live — `· N` (число cue) или «идёт вместе с просмотром» вместо процента.
- Нативный MP4 с `mov_text` без транскодера — вне охвата (нет сессии транскодера); чип AI не
  предлагается, как сейчас.

## Риски

- Перевод отстаёт от просмотра на батч (до ~10–20 с речи + ответ модели): первые минуты зритель
  видит AI-субтитры с задержкой; после финала — полный файл из кэша для следующих зрителей.
- Перемотка вперёд: транскодер стартует новую сессию с новой точки; плейлист меняется — у
  сервиса это новый `X-Source-Url`? Нет: путь плейлиста тот же, содержимое другое. Нужно
  учитывать `#EXT-X-SESSION-OFFSET` (сдвиг cue) и не считать пропущенный диапазон
  «переведённым». Финал в S3 фиксируется только если покрыта вся длительность (иначе остаётся
  в Redis как частичный, `Live` снимается, но `final` не пишется).
- Стоимость та же, что у приложенных субтитров; батчи мельче → на ~20–30 % больше входных
  токенов из-за повторяющегося промпта.
